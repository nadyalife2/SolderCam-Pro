## 1. Кастомное рекавери: сначала бэкап, потом прошивка

На шаге 2 мы договорились не рисковать стоковыми разделами вслепую. Смартфон у нас на OxygenOS 11 с A/B разметкой, но в отличие от многих чистых A/B девайсов, у Nord N10 есть полноценные физические разделы рекавери: `recovery_a` (`/dev/block/sde14`) и `recovery_b` (`/dev/block/sde37`).

Что я сделала перед любыми манипуляциями с загрузчиком:
1. **Слила полные дампы стоковых разделов:** вытащила `recovery_a.img` (104 857 600 байт) и `recovery_b.img` (104 857 600 байт) прямиком на ПК в папку `BACKUP_ONEPLUS_NORD_N10_BILLIE/`.
2. **Проверила TWRP «на весу»:** через `fastboot boot Twrp_3.5.2-10_EduardoA3677-billie_OxygenOs11_Android11.img` загрузила образ прямо в оперативку. Загрузчик отработал за 1.5 секунды, экран ожил, интерфейс TWRP 3.5.2 поднялся без единого зависания.
3. **Проверила F2FS-дешифрование:** TWRP подцепил ключ, расшифровал раздел данных (`/dev/block/dm-10 on /data type f2fs`) и увидел все 90 ГБ свободного места в `/sdcard`. Никаких запросов паролей или битых символов.
4. **Тестовый бэкап Boot:** через консольный интерфейс `twrp backup B` сняла резервную копию ядра и ramdisk в `/data/media/0/TWRP/BACKUPS/` со скоростью 96 МБ/с.
5. **Зашила намертво:** убедившись в стабильности, прошила образ в оба слота:
   ```bash
   fastboot flash recovery_b Twrp_3.5.2-10_EduardoA3677-billie_OxygenOs11_Android11.img
   fastboot flash recovery_a Twrp_3.5.2-10_EduardoA3677-billie_OxygenOs11_Android11.img
   fastboot reboot
   ```

Результат: стоковая OxygenOS 11 грузится без сучка и задоринки, рут Magisk на месте, а при перезагрузке в рекавери нас всегда встречает полноценный рабочий TWRP с возможностью спасти любой кирпич.

## 2. Грабли с AID_INET: почему сокеты в фоне вылетали с ошибкой

Когда я настроила запуск наших нейросетевых демонов (`llama-server`) через скрипт `start_reflex.sh`, меня ждал классический сюрприз безопасности Android. 

В логах `reflex.log` и `embed.log` красовалось:
```text
E srv  start: couldn't bind HTTP server socket, hostname: 0.0.0.0, port: 8081
E srv  start: couldn't bind HTTP server socket, hostname: 0.0.0.0, port: 8082
```

Казалось бы: порт свободен, процесс запускается под пользователем Termux `u0_a234` (UID 10234). В чем затык?
Оказалось, когда мы дергаем скрипт через Magisk `su u0_a234`, `su` переключает UID, но **отсекает дополнительные GID приложения**! В Android непривилегированному процессу для вызова `socket(AF_INET, SOCK_STREAM)` жизненно необходима группа **`AID_INET` (GID 3003)**. Без нее ядро отбивает бинд сетевого сокета ошибкой `EACCES (Permission denied)`.

Я решила это в лоб через флаги MagiskSU:
```bash
su -g 10234 -G 3003 u0_a234 -c '...'
```
Мы явно сохранили основную группу `10234` и передали `3003 (inet)`. В ту же секунду оба демона радостно открыли сокеты и встали в `LISTEN` на `0.0.0.0`!

## 3. Сквозной боевой тест: Reflex CoT и эмбеддинги 1024-dim

Проверяем здоровье ноды:
- **Порт 8081 (Reflex LLM `LFM2.5-8B-A1B` IQ3_XXS):** отправляем POST-запрос с коротким промптом `"Say READY"`. Модель не просто выдает ответ, она включает встроенный Extended Thinking (Reasoning CoT) прямо на 2 ядрах Cortex-A77:
  ```json
  {
    "choices": [{
      "message": {
        "role": "assistant",
        "reasoning_content": "\nOkay, the user sent \"READY\""
      }
    }],
    "timings": { "predicted_per_second": 2.35, "prompt_per_second": 2.21 }
  }
  ```
- **Порт 8082 (Vector Engine `BGE-M3` Q8_0):** запрос `/embedding` возвращает честный 1024-мерный плотный вектор эмбеддинга для базы знаний кластера.
- **Порт 8022 (OpenSSH):** терминальный доступ по SSH доступен по всей локальной сети.

## 4. Защита батареи 24/7 (Battery Guard)

Смартфон на роли вычислительной ноды будет висеть на зарядном кабеле постоянно. Если держать Li-ion на 100% при постоянных 4.4 В и нагреве от CPU, аккумулятор вздуется за пару месяцев.

Я раскопала аппаратные sysfs-ноды контроллера заряда Qualcomm PM7250B / BQ27541 на нашем аппарате:
- `/sys/class/power_supply/battery/charging_enabled`
- `/sys/class/power_supply/battery/input_suspend`

Когда мы пишем `0` в `charging_enabled`, PMIC моментально физически отключает подачу тока на банку аккумулятора. Питание смартфона переходит в режим сквозного питания с кабеля!

Я развернула фоновый сторожевой скрипт `~/battery_guard_24x7.sh`:
- При достижении 78% заряда он отключает зарядку (`charging_enabled = 0`).
- Телефон живет от адаптера, батарея отдыхает в диапазоне ~3.9 В без деградации электролита.
- Если заряд опускается ниже 70%, скрипт включает зарядку обратно (`charging_enabled = 1`).
